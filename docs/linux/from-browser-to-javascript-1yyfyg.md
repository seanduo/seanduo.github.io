# 从浏览器到 JavaScript

## 浏览器的诞生：文档的查找与关联

1989 年，英国计算机科学家 Tim Berners-Lee 在欧洲核子研究中心（CERN）工作。

当时研究机构有大量文档，存放在不同计算机中。问题是，**这些文档分散在不同系统中，查找和关联都很不方便**。

Tim Berners-Lee 希望实现这样一种功能：我打开一份文档，看到其中提到另一份文档，就能直接点击跳转过去，即使另一份文档保存在另一台计算机中。现在看来非常普通，但当时是一个重要创新。

为了实现这个目标，需要解决以下这几个问题：

> - 如何描述文档的结构和链接？
> - 如何从另一条计算机获取文档？
> - 如何让用户查看和跳转文档？

针对上述三个问题，分别设计了 HTML、HTTP 和 浏览器。

所以 HTML、HTTP、URL 和浏览器不是相隔很多年才出现的，而是同一个 Web 系统的配套设计。

到 1990 年年底，这套系统已经有可运行的原型。它叫 WorldWideWeb，后来改名为 Nexus，以免与万维网本身混淆。

这个浏览器用 Objective-C 编写，其源代码经编译器编译为 NeXT 平台上的原生程序；操作系统加载该程序并启动浏览器。浏览器可读取 HTML 文档，解析后显示其中的文本和链接。

> 早期浏览器只需要理解 HTML 这类**文档格式**，以及访问远程文档的**网络协议**。
>
> 一份简单网页只需要：从**服务器**获取 HTML → **解析** HTML → 识别标题、段落、超链接 → 计算布局 → 绘制到屏幕

## JavaScript：网页自己处理部分逻辑

假设在 1994 年你想开发一个登录网页，早期实现的典型过程是：用户输入账号密码 → 点击登录 → 浏览器向服务器发送请求 → 服务器检查账号密码 → 服务器**返回新的 HTML** → 浏览器显示结果

如果你只想在用户提交之前检查一下密码是否为空呢，难道也要发送一次网络请求吗？开发者自然会想到：

> 能不能在浏览器内部提供一种编程语言，让网页自己处理一些逻辑？

于是，1995 年，Netscape 公司的 Brendan Eich 开发了 JavaScript。从此网页不只是可以被查看的文档，还能包含可执行的交互逻辑。

浏览器不是因为 JavaScript 才出现的，而是浏览器发展到一定阶段，才产生了在网页中执行程序逻辑的需求。

## TypeScript：在 JavaScript 基础上增加静态类型系统

JavaScript 是动态类型语言。变量的类型在运行时确定，而且变量可以在不同时间引用不同类型的值。这带来了灵活性，但也带来了问题。

如果函数参数的类型不符合预期，很多错误可能要等到运行时才暴露。于是，开发者提出一个想法：

> 能不能在代码运行之前，就检查出这些类型错误？

这就引出了 TypeScript。需要注意的是 TypeScript 通常不能直接交给普通 JavaScript 运行环境执行。它通常需要先转换成 JavaScript。因为 TypeScript 的类型检查主要发生在开发和编译阶段，而不是运行阶段。

> TypeScript 源代码 → TypeScript 编译器 → 静态类型检查 → 转换代码 → JavaScript 代码 → JavaScript 引擎 → 执行

## Node.js：操作系统执行 JavaScript

成熟的 JavaScript 引擎 + 事件驱动编程习惯 + 异步 I/O，可以组成一种很方便的服务器开发平台。Node.js 官方也将它定位为面向可扩展网络应用的异步事件驱动 JavaScript 运行环境。

> 为什么大型企业经常选择 Java，而不少 Web 全栈团队更倾向于 TypeScript + Node.js？
>
> - 大型企业倾向于保留 Java，不一定是因为 Java 在每个技术指标上都更好，而是因为既有生态和迁移成本同样重要
> - 对于团队人数有限、前后端都需要频繁修改的 Web 项目，这种语言和工具链的统一很有吸引力。
